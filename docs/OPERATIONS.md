# 실행과 운영 검수

## 경로와 환경

`APP_DATA_DIR` 기본값은 저장소의 `.runtime`입니다. DB 파일·해시 기반 파일 객체·서명 키·데모 토큰은 이 디렉터리에 생성하며 Git에서 제외합니다. PostgreSQL에서는 `DATABASE_URL`을 API·Worker·CLI에 동일하게 주입합니다. 파일 저장소 경로 역시 공유해야 합니다.

서버 시작 전에 `python -m app.cli init` 또는 빈 DB에서 `demo`를 실행합니다. Worker를 실행하지 않으면 비동기 작업은 대기 상태로 남습니다. 서버를 종료해도 DB의 작업·버전·승인 기록은 유지됩니다.

## 승인 작업 순서

|대상|작성 역할|독립 검토와 승인|
|---|---|---|
|데이터·분석|ANALYST|다른 REVIEWER 또는 LEAD|
|기사|EDITOR / SEARCHER|다른 REVIEWER 또는 LEAD|
|팩트체크|REVIEWER|검증자·기사 작성자와 다른 REVIEWER 또는 LEAD|
|공개 묶음|EDITOR / LEAD|다른 LEAD|

검토 화면의 차단 사유를 모두 해소하고 최신 ETag로 기록합니다. 내용 변경은 이전 데이터 승인을 무효화하며 품질 검사를 다시 요구합니다. 412 충돌이면 사용자의 편집 내용을 보존한 상태에서 최신 버전을 조회합니다.

## 장애 처리

- `JOB_FAILED`: 작업 오류를 확인하고 원본·권한·범위를 수정한 뒤 새 멱등 키로 다시 요청합니다.
- `RESOURCE_BUSY`: 같은 작업본을 처리하는 Job이 끝난 뒤 상세 상태와 ETag를 다시 조회합니다.
- `APPROVAL_REQUIRED`: 응답의 blocking_issues를 확인합니다. 승인·근거·FC·파일 검수 중 어떤 조건이 빠졌는지 표시됩니다.
- Worker 종료: 5분 임대 만료 후 재접수할 수 있습니다. 현재 로컬 작업은 짧은 단일 트랜잭션을 사용합니다.
- 데이터 수정: 고정된 기준본을 직접 변경하지 말고 새 DRAFT에서 원본을 다시 가져옵니다.
- 공개 철회: 총괄이 사유를 기록합니다. 이후 공개 API와 다운로드는 410을 반환합니다.

## 백업

API·Worker를 정지한 뒤 SQLite DB와 전체 파일 저장소를 같은 시점으로 보관합니다. PostgreSQL은 일관된 DB 백업과 파일 객체 목록·해시를 묶어 보관합니다. 복원은 별도 환경에서 파일 해시·FK·승인·공개 상태와 다운로드를 확인한 뒤 공개를 재개합니다. 백업 자동화·보관 기간·RPO/RTO는 이 커밋에서 보장하지 않습니다.

## 보안 경계

로컬용 데모 계정 선택 기능은 `APP_DEMO_MODE=1`에서만 열립니다. 외부 배포 시 반드시 끄고 데모 DB를 사용하지 않습니다. 발급 토큰과 `.runtime` 전체를 공개 저장소에 추가하지 않습니다. 토큰은 DB에서 SHA256 해시와 만료 시각으로 관리합니다.

원본 파일은 임의 URL에서 다운로드하지 않습니다. 이 구현은 사용자 파일 업로드만 받으므로 수집용 SSRF 경로가 없습니다. 파일 저장 경로는 해시 기반으로 생성하고 클라이언트가 경로를 지정할 수 없습니다. 구조화 기사 본문은 HTML로 실행하지 않고 이스케이프합니다. 운영 DB 계정과 파일 저장소는 서버 프로세스에만 허용하세요.

## 확인한 범위

로컬 SQLite 통합 시험과 실제 브라우저의 독자·관리 화면을 검수했습니다. PostgreSQL 연결 시험은 CI 서비스에서 추가 실행하도록 설정했습니다. Docker 빌드·외부 OIDC·외부 LLM·멀티 인스턴스 부하·침투 시험은 수행하지 않았습니다.
